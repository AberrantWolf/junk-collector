# Junk Collector v0.1.0-beta.3

Beta.3 improves large imports and automatically groups clear multidisc albums.
It remains a prerelease for backed-up home-lab use. The Container release workflow
passed both native architectures and anonymous image verification. The published
bundle pins the verified digest. See [publication evidence](../validation/container-beta3-publication-2026-10-22.md);
actual beta.3 NAS deployment remains an operator check.

## What's new

- Background processing defaults to four workers, configurable from one to eight,
  with a separate inbox-copy cap and one provider-download slot. Ready metadata
  and copied-disc processing receive bounded priority without starving other work.
  See [worker settings](../configuration.md#background-workers).
- Imports distinguish active, queued, waiting and cancelling work, including shared
  provider downloads. Work filters and Activity's Back navigation are improved.
- Clear MusicBrainz disc membership groups entries automatically, including cases
  where the album metadata choice remains unresolved. Originals, physical copies,
  manual authority and historical evidence are retained. Conflicting or unproven
  membership stays available for review. Guarded undo retains explicit separation.
- Review repairs preserve reset metadata authority and completed import outcomes,
  and prevent a late draft load from overwriting an immediate source choice.

Automatic grouping applies to existing eligible entries during recovery, not only
new imports. It does not establish catalog or audio verification and does not
infer that separate physical copies form one purchased set. See
[acceptance and limits](../validation/automatic-album-grouping-2026-10-22.md).

## Image and Portainer update

```text
ghcr.io/aberrantwolf/junk-collector:v0.1.0-beta.3
```

The release workflow builds linux/amd64 (including Synology DS1522+) and linux/arm64,
verifies anonymous pulls, and publishes an installation bundle with a pinned digest.
`preview` follows prereleases; stable `latest` is not advanced.

1. Keep the current image digest, stop Collector, and create a consistent recovery
   point covering archive, private state and config/TLS using the existing
   [snapshot](../../deploy/container/snapshot-recovery.md) or
   [full-backup procedure](../../deploy/container/recovery.md).
2. Set the Portainer stack's `COLLECTOR_IMAGE` to this release's verified digest
   (or the version tag above). Keep the existing mounts, config and credentials.
3. Use **Update the stack** with image re-pull enabled, following the
   [Portainer update instructions](../../deploy/container/README.md#update).
   Do not rerun fresh setup. Confirm beta.3 startup, sign-in, library, import
   activity and playback after the update.

Private schema remains **21**. The disposable catalog rebuilds to **15** from
preserved records; original payloads are not hashed by that rebuild. Allow startup
to finish. Automatic grouping can write new portable revisions after startup.
After new writes, rollback requires the matching recovery point and old image;
an image-only downgrade is not a recovery plan.

## Qualification limits

Source checks and isolated Chrome journeys cover the new workflows. Native
container runtime, both architectures and public pulls are gates in the release
workflow. Actual beta.3 NAS/Portainer deployment remains a separate operator check;
earlier beta.2 deployment evidence is not a beta.3 update result.

LAN DNS, trusted local proxy, relay and native route-switching documents in this
release are plans only. No live DNS/proxy changes or automatic transport failover
are implemented by beta.3. Collector does not remove the extra inbox staging copy.
