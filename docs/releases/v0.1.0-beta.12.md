# Junk Collector v0.1.0-beta.12

Library browsing now reads compact server-cached summaries rather than rebuilding
complete track/profile availability and sending capture/file graphs for every
page. Rows retain their titles, artwork, playback attention and per-original
AccurateRip status. Album details and management panels still load fresh full
records when opened.

The rebuildable cache separates roles, metadata languages and module/presentation
versions. Current authorization is checked on reads. Inventory, metadata,
assignments, artwork, preparation and audio-result changes invalidate summaries;
concurrent changes cannot publish a cache row against a newer projection token.
Import progress stays live without expiring rows on job heartbeats. At most twelve
disposable variants are kept per item. Unchanged rows survive a server restart.

A cold or invalidated row still runs the existing detailed resolver once. First
use after this upgrade/reindex, new language/role variants and collection-wide
artwork/identity invalidations can therefore take longer than repeat loads. No
audio algorithms, verification coverage, raw originals or metadata authority change.

## Installation and recovery

Use `ghcr.io/aberrantwolf/junk-collector:v0.1.0-beta.12` or the immutable digest in
the published `release-image.json`. This prerelease advances `preview`; stable
`latest` is unchanged. Update core and media together, retaining configuration,
identity/TLS, archive, private state, mounts and media sockets. Do not rerun setup.

The upgrade adds disposable cache tables alongside the existing catalog index;
it does not force a full index rebuild. Catalog record, portable archive and
private-state formats are unchanged; existing queued/interrupted jobs remain
durable. Explicit reindex discards derived cache entries and reconstructs them on
use. No collection evidence or accepted metadata/artwork is compacted or deleted.

Retain the old image and a complete stopped-server recovery point using the
[existing snapshot procedure](../../deploy/container/snapshot-recovery.md). Rollback
uses that matching complete recovery point and old image. No new library batch is
automatically submitted by deployment.
